# Модель угроз MindGuard v1

> **Статус документа:** модель угроз **Optional Binary Integrity Bridge** и его
> фиксированного Protocol v1. Она не является моделью Static Protection SDK; для
> static literals, build/cache/debug-symbol и residual runtime рисков см.
> [static-threat-model.md](static-threat-model.md). Форматные и signing-правила
> Bridge не изменяются новым static contract.

## Назначение и границы

MindGuard v1 — локальный комплект из внешнего `Protector` (CLI на Rust), который подготавливает файл перед поставкой, и встроенного `Runtime SDK` (независимые реализации на Rust и C++). Сеть, веб-панель и обязательный сервер отсутствуют. SDK проверяет файл текущего процесса до начала чувствительной работы приложения.

Эта модель описывает целостность файла и обнаружение вмешательства в пределах протокола v1. Она не утверждает, что приложение невозможно взломать, и не расширяет объём, зафиксированный в `plan.md`.

## Активы

| Актив | Что требуется защитить | Последствие потери |
|---|---|---|
| Финальный бинарный файл | Код, данные, заголовки, таблицы, выравнивание и все байты вне диапазона метаданных | Запуск изменённого артефакта |
| Блок метаданных | `metadata_offset`, `metadata_size`, `trusted_key_id`, дайджест SHA-256 и подпись Ed25519 | Неверная область покрытия или обход проверки |
| Доверенный открытый ключ | Ключ, заданный сборкой приложения/SDK | Принятие подписи злоумышленника |
| Закрытый ключ подписи | Внешний секрет только для `Protector` | Выпуск произвольных файлов |
| Решение SDK | «Успех — продолжить, ошибка — завершить» | Небезопасное продолжение |
| Форматные таблицы | Корректные смещения ELF/PE/Mach-O | Повреждение загрузчика или разное поведение SDK |

## Доверенные компоненты и корень доверия

1. **Открытый ключ в приложении/SDK** — корень доверия v1. Он поставляется вне метаданных (скомпилированный массив байтов или эквивалентная конфигурация) и не заменяется значением из проверяемого файла.
2. **Закрытый ключ и среда сборки/CI** считаются доверенными при выпуске. Закрытый ключ загружается `Protector` только из внешнего файла/секрета и не попадает в артефакт, SDK, журнал или fixture.
3. **Код `Protector`, SDK и криптография** считаются корректными и проверенными тестами; входные байты для парсера всегда недоверенны.
4. **ОС и файловая система** считаются честными в локальной модели (обычный пользователь не может подменить ядро или системные примитивы). SDK проверяет ошибки чтения через дескриптор/handle.

Если атакующий изменяет сборку SDK, приложение, ключ, загрузчик, ядро или гипервизор, эти предположения нарушены и корень доверия больше не действует.

## Возможности атакующего

В пределах модели атакующий может:

- читать поставленный бинарный файл и публичные метаданные;
- изменять, удалять, добавлять или переставлять байты до запуска, включая код, данные, заголовки, таблицы, секции и блок метаданных;
- заменить файл другим локальным файлом, обрезать его, создать дубликаты секций и изменить форматные смещения;
- запускать `Protector` с повреждённым/неподдерживаемым входом или неверным ключом и наблюдать код ошибки (закрытый ключ ему недоступен);
- многократно запускать приложение и анализировать отказ.

Без закрытого ключа и без изменения доверенного SDK изменение любого покрытого байта должно приводить к отказу с вероятностью, определяемой криптографическими предположениями SHA-256 и Ed25519.

### Явные нецели

В v1 не обещаются: атакующий, укравший закрытый ключ или заменивший доверенный ключ; патч приложения/SDK, DLL/interpose-подмена или загрузчика; `root`/администратор и контроль ядра, гипервизора либо среды виртуализации; изменение памяти после проверки, debugger/anti-debugging, обнаружение VM, memory-patch detection и runtime hardening; обфускация, VM-based code virtualization, licensing/entitlements; веб-интерфейс, централизованный/backend-сервис, сеть, удалённая отзывка; kernel/driver components, HSM, автоматическое Authenticode или Apple code signing; защита от replay старого, но корректно подписанного артефакта.

## Локальные допущения

- `Protector` запускается на доверенной машине сборки, создаёт новый файл и не меняет `--input`; выход записывается атомарно, ошибка не оставляет частичного результата.
- Закрытый ключ поступает из внешнего файла размером 32 байта (Ed25519 seed) либо из секрета CI, материализованного в такой файл. В репозитории и бинарниках его нет.
- Открытый ключ заранее доставлен приложению/SDK: 32 сырых байта Ed25519 (каноническая конфигурация — 64 строчных hex-символа).
- SDK работает офлайн и не получает ключ или решение от сервера.
- SDK читает собственный исполняемый файл штатным механизмом платформы и проверяет стабильность чтения насколько позволяет ОС; гонка с привилегированным писателем — остаточный риск.
- Поддерживаются только явно перечисленные в `protocol-v1.md` варианты ELF, PE и Mach-O для x86_64. Небезопасный вход отклоняется, а не переписывается «на глаз».

## Гарантии целостности и anti-tamper

При сохранении допущений и отсутствии криптографического подлога v1 гарантирует:

1. Ровно один именованный блок MindGuard. Отсутствующий, неизвестный, дублированный, усечённый или структурно неверный блок даёт отказ.
2. SHA-256 вычисляется по финальному файлу после форматных обновлений, исключая только точный диапазон `[metadata_offset, metadata_offset + metadata_size)`. Заголовки, таблицы, код, данные, overlay и выравнивание вне диапазона покрываются.
3. `metadata_offset` и `metadata_size` подписаны; подмена области, версии, формата, правила покрытия или `trusted_key_id` обнаруживается.
4. Ed25519 проверяется относительно ключа приложения; ключ из метаданных сам по себе доверием не является.
5. Rust и C++ SDK выдают одинаковый результат для каждого эталонного вектора (`golden fixture`) и мутации.

Это обнаружение изменений, а не абсолютная защита. Замена доверенного ключа вместе с приложением/SDK означает потерю гарантии.

## Границы доверия

1. **Сборка → артефакт.** `Protector` получает недоверенный вход, но доверяет внешнему ключу и реализации; результат публикуется только после самопроверки и атомарной записи.
2. **Файловая система → SDK.** Байты и таблицы полностью недоверенны. Парсер не следует указателям за пределы файла, проверяет переполнения и неоднозначные контейнеры отвергает.
3. **Конфигурация ключа → SDK.** Открытый ключ — внешняя граница доверия. Метаданные сообщают `trusted_key_id`, но SDK сравнивает его с SHA-256 настроенного ключа.
4. **SDK → приложение.** До успешного `verify_or_terminate()` чувствительная работа не начинается. После успеха процесс и память всё ещё находятся вне защиты v1 от привилегированного контроля.

## Политика отказа

`Protector` при ошибке разбора, формата, ключа, криптографии или записи завершается с ненулевым кодом, не заменяет `--output` и не изменяет `--input`.

`verify_or_terminate()` одинаков для Rust и C++:

- при успехе возвращает управление приложению;
- при любой ошибке (невозможно найти/прочитать файл, неизвестны формат или версия, отсутствуют/дублируются/искажены метаданные, неверны ключ, подпись или дайджест) не возвращает управление и немедленно вызывает аварийное завершение без раскрутки стека (`abort`-семантика платформы);
- диагностический код/строка допустимы лишь в тестовом режиме и не превращают отказ в продолжаемое выполнение; боевой путь не полагается на журнал или сеть.

Числовой exit status после `abort` не является частью контракта.

## Жизненный цикл ключей

1. Пара генерируется вне репозитория. Внешний `--key-file` содержит ровно 32 байта seed; другие размеры отвергаются. Файл хранится с минимальными правами (например, `0600` на Unix) или в защищённом секрете CI.
2. `Protector` выводит стандартный (совместимый с RFC 8032) 32-байтный открытый ключ Ed25519 из seed, вычисляет `trusted_key_id = SHA-256(public_key_bytes)` и подписывает метаданные. Seed не записывается в output, SDK, логи, fixtures или ошибки; память следует занулить после использования (с оговоркой о гарантиях конкретного рантайма).
3. В приложение/SDK встраивается или задаётся только открытый ключ. Строчная форма `hex` и преобразование описаны в `protocol-v1.md`.
4. Ротация ключа — новая сборка приложения/SDK с новым открытым ключом и повторная защита. Списки ключей и онлайн-отзыв v1 не определены; старый артефакт принимается, пока соответствующий ключ явно доверен.
5. При компрометации seed его удаляют из CI/хранилища и выпускают новую сборку; локального/сетевого механизма отзыва нет.

## Остаточные риски

- Компрометация закрытого ключа, сборочной машины, приложения или SDK позволяет выпускать/принимать изменённые файлы и находится за границей модели.
- SHA-256 и Ed25519 опираются на современную криптографическую стойкость; поломка потребует новой версии протокола.
- Гонка TOCTOU между поиском пути и открытием файла на доступной атакующему ФС; дескриптор и проверки размера уменьшают, но не устраняют риск.
- Проверка файла не проверяет уже загруженные страницы: отладчик, динамические зависимости, JIT и изменение памяти не покрыты.
- Старый корректно подписанный бинарник можно воспроизвести; freshness/версия выпуска должна контролироваться доставкой.
- Ошибки независимых парсеров Rust/C++ или загрузчика могут привести к отказу либо уязвимости; поэтому требуются общие эталонные наборы (`golden fixtures`) и негативные мутации.
- Безопасные ограничения PoC для PE и Mach-O могут отклонить реальные файлы (например, Authenticode/Apple-подписанные или без места для команды загрузки (`load command`)), а не обещают произвольное переписывание.
