# Протокол встроенных метаданных MindGuard v1

> **Статус документа:** это фиксированный контракт **Optional Binary Integrity
> Bridge** (текущий фактически проверенный срез — ELF64LE x86_64 Linux). Он не
> описывает основной Static Protection SDK. Новый static blob и его API находятся в
> [static-protection-v1.md](static-protection-v1.md), а отдельная модель угроз — в
> [static-threat-model.md](static-threat-model.md). Правила 512-байтного блока ниже
> не расширяются и не изменяются Static SDK.

## Статус и область применения

Документ является нормативным контрактом для внешнего `Protector` (CLI на Rust) и
независимых `Runtime SDK` на Rust и C++. Реализации не используют общее ядро или
`C ABI`; совпадение обеспечивается только этим документом и общими эталонными наборами (`golden fixtures`).
Все приведённые байты и числа однозначны. Любое неописанное расширение в v1 запрещено.

Поддерживаемые варианты: ELF64 little-endian для x86_64 Linux, PE32+ для x86_64
Windows и 64-битный little-endian Mach-O для x86_64 macOS. Protector может безопасно
отклонить файл, который не соответствует ограниченному контракту ниже; он не обещает
произвольное переписывание всех бинарников.

## Нормативные правила

- Используются только SHA-256 и чистая (без prehash/context) Ed25519.
- В финальном файле должен быть ровно один блок MindGuard. Отсутствующий,
  неизвестный, дублированный, усечённый или структурно неверный блок даёт fail-closed.
- Дайджест вычисляется по финальному файлу после всех форматных изменений, исключая
  только байты диапазона `[metadata_offset, metadata_offset + metadata_size)`. Все
  остальные байты, в том числе заголовки, таблицы, выравнивающие промежутки и overlay,
  покрываются.
- Числовые поля имеют little-endian представление. В протоколе нет optional-полей,
  сжатия, TLV, padding с неопределённым содержимым или альтернативной
  сериализации.
- `trusted_key_id` и все криптографические поля имеют фиксированный размер. Открытый
  ключ берётся из конфигурации приложения/SDK; значение из файла никогда не становится
  корнем доверия.
- При любой неоднозначности, переполнении, неизвестном значении или ошибке чтения
  проверка завершается отказом.

## Размещение блока в контейнере

| Формат | Точное имя | Требование к содержимому |
|---|---|---|
| ELF64 | секция `.mindguard` | `SHT_PROGBITS`, `sh_size = 512`, `sh_offset = metadata_offset`, без `SHF_ALLOC` |
| PE32+ | секция `.mguard` | поле имени ровно 8 байт: ASCII `.mguard` и один `NUL`; `VirtualSize = SizeOfRawData = 512` |
| Mach-O 64 | секция `__mindguard` внутри сегмента `__MINDGUARD` | имена NUL-дополнены до 16 байт; секция и сегмент имеют файл-диапазон ровно 512 байт |

Имена сравниваются по их полям фиксированной длины, а не по строке, завершающейся
первым случайным `NUL`. Для ELF имя получается только через проверенную таблицу
строк. В каждом формате имя ровно одно. Второе такое имя — `METADATA_DUPLICATE`.
Имя с тем же зарезервированным префиксом, но с иным хвостом (например, `.mguardX`),
считается неизвестным MindGuard-блоком и отвергается как `METADATA_UNKNOWN`; обычные
данные без этого префикса являются покрываемыми данными.

`metadata_offset` должен совпадать с offset секции в формате, а `metadata_size` — быть
ровно `512`. Диапазон должен целиком находиться в файле, не переполнять `u64` и не
пересекать заголовок, таблицы заголовков загрузки/секций, либо файл-диапазон любого другого
объекта формата. Это не позволяет исключить из дайджеста заголовок или таблицу под
видом метаданных.

## Фиксированный бинарный блок

Размер блока всегда **512 байт**. Все смещения ниже отсчитываются от начала секции. Поля `u16`,
`u32`, `u64` — little-endian. Массивы байт записываются слева направо без кодирования `hex`/`base64`.

### Заголовок (32 байта)

| Смещение | Размер | Поле | Значение/правило |
|---:|---:|---|---|
| `0x00` | 8 | `magic` | байты ASCII `MGV1META`: `4d 47 56 31 4d 45 54 41` |
| `0x08` | 2 | `protocol_version` | `u16 = 1` |
| `0x0a` | 2 | `header_size` | `u16 = 32` |
| `0x0c` | 1 | `binary_format` | `1 = ELF64LE_X86_64`, `2 = PE32PLUSLE_X86_64`, `3 = MACHO64LE_X86_64` |
| `0x0d` | 1 | `coverage_rule` | `1 = EXCLUDE_EXACT_METADATA_RANGE` |
| `0x0e` | 2 | `reserved0` | все биты `0` |
| `0x10` | 8 | `metadata_offset` | абсолютное файловое смещение начала секции |
| `0x18` | 8 | `metadata_size` | `u64 = 512` |

### Полезная нагрузка и подпись (128 байт)

| Смещение | Размер | Поле | Значение/правило |
|---:|---:|---|---|
| `0x20` | 32 | `trusted_key_id` | `SHA-256(public_key_bytes)` |
| `0x40` | 32 | `artifact_digest` | SHA-256 финального файла без диапазона метаданных |
| `0x60` | 64 | `signature` | Ed25519 над каноническим `signed_prefix` |

Оставшиеся байты `0xa0..0x1ff` (352 байта) — `reserved_tail`; каждый обязан быть
нулём. Их наличие позволяет PE с обычным `FileAlignment = 0x200` иметь ровно один
файл-диапазон секции, не вводя переменный размер. Ненулевой reserved-байт —
`METADATA_MALFORMED`; эти байты не являются скрытым расширением.

### Каноническая последовательность подписи

`signed_prefix` — ровно первые 96 байт блока, то есть последовательность:

```
metadata[0:32]   || metadata[32:64] || metadata[64:96]
  header             trusted_key_id    artifact_digest
```

В частности, в неё входят `metadata_offset` и `metadata_size`, а также magic, версия,
формат и правило покрытия. `signature` и `reserved_tail` в неё не входят. Подпись
вычисляется стандартной Ed25519 над этими 96 байтами без domain-prefix, prehash,
контекста, DER или иной оболочки. Проверяющий передаёт в Ed25519 ровно те же 96 байт.

`trusted_key_id` вычисляется над 32 сырыми байтами Ed25519 public key, а не над их
hex-представлением. Никакая часть открытого ключа не хранится в блоке.


### Строгий профиль Ed25519

Для обеспечения одинаковой классификации в независимых Rust и C++ SDK применяется
только следующий профиль проверки Ed25519. Настроенный открытый ключ и первая половина
подписи `R` обязаны быть каноническими 32-байтными сжатыми кодировками точки Ed25519
(`compressed point encoding`):
это стандартная little-endian кодировка координаты `y` с битом знака `x` в старшем
бите; декодирование должно давать точку с единственным каноническим представлением
(повторная компрессия даёт те же 32 байта), с `y < p`, где
`p = 2^255 - 19`, и точка малого порядка (порядок, делящий `8`) отвергается. Вторая
половина подписи `S` — ровно 32 байта, кодируемые little-endian каноническим скаляром
(`canonical scalar`), и принимается только при `S < L`, где
`L = 2^252 + 27742317777372353535851937790883648493` — порядок основной подгруппы
Ed25519. Неканоническое или недекодируемое
представление настроенного открытого ключа, а также открытый ключ малого порядка,
классифицируются как `MG-V10` (`KEY_CONFIG_INVALID`). Неканоническое или
недекодируемое представление `R`, `S >= L` и точка `R` малого порядка классифицируются
как `MG-V12` (`SIGNATURE_INVALID`).

Профиль использует только чистую Ed25519 над ровно 96 байтами `signed_prefix` и
ровно 64 байтами подписи: prehash, context, DER и любые иные оболочки запрещены.
Если выбранный криптографический модуль (`backend`) не гарантирует каноническое
декодирование, проверку `S < L` и отбрасывание точек малого порядка,
реализация обязана выполнить до вызова модуля (`backend`) валидированную
предварительную проверку (`precheck`) с указанной классификацией либо отвергнуть вход
с fail-closed с тем же кодом (`MG-V10` для настроенного ключа и `MG-V12` для
подписи). Без такой гарантии запрещено молча применять более разрешительную
трактовку Ed25519.

## Жизненный цикл финализации Protector

Ниже приведён единственный нормативный порядок, устраняющий круговую зависимость между
дайджестом, подписью, форматными полями и публикацией. Реализация может использовать
память или временное хранилище (`staging`), но классифицирует ошибки в порядке раздела
«Полная нормативная очередность ошибок» и не публикует результат до завершения всех
предшествующих этапов.

1. Прочитать `--input` целиком. Ошибка чтения даёт `MG-P01`.
2. По magic классифицировать контейнер: неизвестный magic даёт `MG-P03`,
   распознанный, но неподдержанный endian/class/machine — `MG-P04`.
3. Полностью разобрать поддерживаемый контейнер, таблицы, строки, bounds,
   переполнения и пересечения; затем просканировать активные структуры в
   детерминированном порядке и обнаружить точные канонические разделы и псевдонимы.
   Структурная ошибка даёт `MG-P05`; уже существующий канонический раздел или
   зарезервированный префикс-псевдоним — `MG-P06`.
4. Проверить безопасный layout преобразования: pre-insertion slack, число записей,
   выравнивание, нативные ширины и все raw/RVA/virtual endpoint. Непредставимое или
   небезопасное размещение даёт `MG-P07`.
5. Открыть и полностью прочитать внешний `--key-file`; ошибка I/O даёт `MG-P08`.
   Проверить ровно 32 байта seed и отсутствие дополнительных байтов; ошибка синтаксиса
   или длины даёт `MG-P09`.
6. Проверить канонические пути `--input` и `--output`: существующий `--output` либо
   совпадение с `--input` даёт `MG-P11`. Эта проверка выполняется до криптографической
   финализации, чтобы не вычислять и не публиковать результат, который заведомо нельзя
   записать по требуемой identity-политике.
7. Построить полную финальную последовательность байтов в памяти или эквивалентном
   staging без публикации. Добавить форматные структуры и выбрать
   `metadata_offset`; записать нулевой padding и ровно 512 нулевых байт placeholder.
   Форматные заголовки, таблицы, размеры и выравнивание должны уже ссылаться на этот
   offset и размер 512. Получившийся размер и все байты вне диапазона окончательны.
8. Вычислить
   `artifact_digest = SHA-256(output[0:metadata_offset] ||
   output[metadata_offset+512:file_length])` — без дополнительных диапазонов.
   Сформировать первые 96 байт, вычислить `signature = Ed25519.Sign(private_key,
   signed_prefix)` и собрать полный блок: подпись в `0x60`, весь reserved — нули.
   Независимо проверить готовую последовательность байтов алгоритмом SDK с
   соответствующим открытым ключом. Любая ошибка SHA-256, Ed25519 или
   самопроверка (`self-verification`) даёт `MG-P10`; хранилище (`staging`) не публикуется.
9. Создать временный output в том же каталоге и записать в него уже проверенную
   последовательность, выполнить операции `flush`/`sync` согласно возможностям ОС. Ошибка создания,
   записи или `flush` даёт `MG-P02`.
10. Иная непредвиденная ошибка реализации до публикации даёт `MG-P13`; временный
    результат удалить и не публиковать.
11. Сбросить данные/метаданные согласно возможностям ОС и выполнить атомарное
    переименование без замены существующего `--output`. Ошибка атомарной публикации
    (`atomic publication`) или `rename` даёт `MG-P12`; частичный output не считается
    защищённым.

Protector не должен добавлять timestamp, случайный nonce или иные недетерминированные
байты в создаваемые структуры; при одинаковых input и key результат одинаков.

## Алгоритм проверки SDK

`verify_or_terminate()` выполняет следующие этапы в указанном порядке; никакой этап не
может заменить другой. Полная классификация при нескольких условиях зафиксирована в
разделе «Полная нормативная очередность ошибок» ниже.

1. Найти и открыть собственный executable (см. следующий раздел), прочитать его через
   один дескриптор/handle и проверить границы чтения. При ошибке — `MG-V01`
   (`SELF_FILE_IO`).
2. По magic классифицировать контейнер и вариант архитектуры. Неизвестный magic либо
   неподдержанный вариант получает `MG-V02` (`UNSUPPORTED_FORMAT`). Для распознанного
   поддерживаемого варианта полностью разобрать активные заголовки, таблицы, записи,
   строки и все объявленные файловые/виртуальные диапазоны. До завершения этого
   разбора нельзя выдавать результат поиска метаданных. Любая усечённая таблица,
   выход за файл, пересечение, переполнение или иная структурная ошибка даёт
   `MG-V03` (`MALFORMED_FORMAT`).
3. После успешного разбора просканировать активные структуры детерминированно: ELF —
   записи section header в порядке индексов; PE — записи section table в порядке
   индексов; Mach-O — load commands в порядке `ncmds`, а секции внутри каждой команды
   `LC_SEGMENT_64` в порядке записей. Посчитать точные канонические кандидаты и отдельно
   обнаружить каждый псевдоним зарезервированного префикса.
4. Применить приоритет кандидатов из нормативного раздела: дубликат точного кандидата,
   псевдоним, отсутствие точного кандидата либо единственный точный кандидат.
5. Если остался ровно один точный кандидат и нет псевдонимов, проверить его фиксированное
   размещение и содержимое: точное имя/поля формата, размер 512, `metadata_offset`,
   отсутствие пересечений и соответствие активной структуре. Несовпадение даёт
   `MG-V07` (`METADATA_MALFORMED`); объявленная таблицей граница, выходящая за файл или
   переполняющаяся, уже была бы `MG-V03` на этапе 2. Прочитать ровно 512 байт.
6. Поля блока проверять в таком порядке: `magic`; `header_size = 32` и
   `metadata_size = 512`; `metadata_offset` равен offset секции; `binary_format`
   совпадает с фактически разобранным контейнером; затем `protocol_version = 1`;
   `coverage_rule = 1`; `reserved0` и весь `reserved_tail` равны нулю. Нарушение
   magic, размеров, offset, format или reserved даёт `MG-V07`; неизвестная версия —
   `MG-V08` (`VERSION_UNSUPPORTED`), неизвестное правило — `MG-V09`
   (`COVERAGE_UNSUPPORTED`).
7. Разобрать настроенный public key по строгому профилю Ed25519. Неверная длина,
   кодировка, неканоническая точка или точка малого порядка дают `MG-V10`
   (`KEY_CONFIG_INVALID`).
8. Вычислить `trusted_key_id` настроенного ключа и constant-time сравнить с полем
   блока. Несовпадение — `MG-V11` (`KEY_ID_MISMATCH`).
9. Проверить Ed25519 над `signed_prefix` по строгому профилю. Ошибка кодировки `R`,
   неканонический `R`, `S >= L`, точка `R` малого порядка или не подтверждённая
   подпись — `MG-V12` (`SIGNATURE_INVALID`).
10. Вычислить SHA-256 по двум диапазонам, исключив только
    `[metadata_offset, metadata_offset+512)`, и constant-time сравнить с
    `artifact_digest`. Несовпадение — `MG-V13` (`DIGEST_MISMATCH`).
11. Только после всех успехов вернуть управление приложению. Непредвиденная ошибка
    реализации, не относящаяся к уже перечисленной проверке, классифицируется как
    `MG-V14` (`INTERNAL`) и также приводит к отказу.

В боевом режиме любая ошибка из этого списка приводит к немедленному завершению без
возврата (`abort`-семантика). Диагностические коды разрешены лишь тестовому стенду и
не меняют боевое решение.

## Полная нормативная очередность ошибок

### SDK

После успешного чтения executable и классификации поддерживаемого варианта SDK обязан
сначала завершить **полный структурный разбор контейнера**: активные заголовки и
таблицы, их размеры и записи, таблицы строк, все файловые и виртуальные диапазоны,
проверки переполнения и пересечений. Любая структурная ошибка контейнера, таблицы или
диапазона немедленно даёт `MG-V03`; результат кандидата метаданных в этом случае не
рассматривается. Это правило действует и тогда, когда повреждённый диапазон содержит
имя `.mindguard`, `.mguard`, `__MINDGUARD` или `__mindguard`.

Только после полного разбора SDK сканирует активные структуры в порядке, указанном на
этапе 3, и считает `exact_count` точных канонических кандидатов и наличие
`reserved_prefix_alias`. При нескольких одновременно выполняющихся условиях выбирается
первая применимая ветвь ровно в таком порядке:

1. `exact_count > 1` — `MG-V05` (`METADATA_DUPLICATE`);
2. иначе, если обнаружен любой `reserved_prefix_alias` — `MG-V06`
   (`METADATA_UNKNOWN`);
3. иначе, если `exact_count = 0` — `MG-V04` (`METADATA_ABSENT`);
4. иначе (ровно один точный кандидат и псевдонимов нет) проверяется фиксированное
   размещение/содержимое, и их несовпадение даёт `MG-V07` (`METADATA_MALFORMED`).

Таким образом, дубликат точного канонического раздела всегда опережает псевдоним;
псевдоним опережает отсутствие точного раздела. После ветви 4 применяются проверки
полей блока в точно установленном порядке `magic` → размеры → offset → format →
`protocol_version` → `coverage_rule` → `reserved`, затем конфигурация открытого ключа
(`MG-V10`), `trusted_key_id` (`MG-V11`), подпись (`MG-V12`) и дайджест (`MG-V13`).
`MG-V01` и `MG-V02` возникают соответственно до этого алгоритма при ошибке чтения либо
неподдержанном magic/варианте; `MG-V14` — только необработанный внутренний сбой после
исключения всех перечисленных причин.

### Protector CLI

Protector классифицирует любую команду `protect` как если бы проверки выполнялись в
следующем порядке, и не может заменить код более поздней ветви кодом более ранней
обнаруженной впоследствии операции:

1. чтение `--input` целиком — `MG-P01` (`INPUT_IO`);
2. классификация контейнера и архитектуры: неизвестный magic — `MG-P03`
   (`UNSUPPORTED_FORMAT`), распознанный magic с неподдержанными endian/class/machine —
   `MG-P04` (`UNSUPPORTED_ARCH`);
3. полный разбор поддерживаемого контейнера, таблиц, bounds и арифметики — `MG-P05`
   (`MALFORMED_INPUT`);
4. уже существующий точный канонический раздел либо любой его зарезервированный
   префикс-псевдоним — `MG-P06` (`DUPLICATE_METADATA`);
5. невозможность безопасно разместить или преобразовать структуры, включая
   непредставимые в нативных полях смещения/размеры, — `MG-P07` (`UNSAFE_LAYOUT`);
6. невозможность открыть или полностью прочитать `--key-file` — `MG-P08`
   (`KEY_IO`);
7. синтаксис, длина или иное несоответствие формату key-file — `MG-P09`
   (`KEY_INVALID`);
8. проверка канонических путей `--input`/`--output`: существующий `--output` либо
   совпадение с `--input` — `MG-P11` (`OUTPUT_EXISTS`);
9. ошибка SHA-256/Ed25519 или независимой самопроверки (`self-verification`) готового результата —
   `MG-P10` (`CRYPTO_FAILURE`);
10. ошибка создания/записи/flush временного output — `MG-P02` (`OUTPUT_IO`);
11. иная непредвиденная ошибка реализации до публикации — `MG-P13` (`INTERNAL`);
12. ошибка атомарной публикации/rename — `MG-P12` (`ATOMIC_RENAME`).

Порядок 8 является нормативным: `--output` проверяется после успешных чтения и
проверки key-file, но до криптографической финализации; это исключает публикацию в
существующий файл. Гонка, при которой файл появляется после этой проверки, является
ошибкой атомарной публикации и классифицируется как `MG-P12`, а не как `MG-P11`.
Если одновременно присутствуют несколько условий, побеждает первая применимая причина
из списка 1–12 (например, дубликат и небезопасный layout дают `MG-P06`, а ошибка
структуры и дубликат — `MG-P05`).

## Как SDK находит свой executable

Путь не берётся из аргумента пользователя и не из метаданных файла.

- Linux: получить `/proc/self/exe`, открыть разрешённый для чтения дескриптор с
  `O_CLOEXEC`, получить размер через `fstat` и читать до EOF. Отсутствие procfs,
  ошибка открытия, чтения или изменение размера — отказ.
- Windows: получить путь текущего модуля через `GetModuleFileNameW(NULL, ...)` с
  повторением при усечении; открыть его `CreateFileW` только для чтения с совместным
  чтением, зафиксировать размер и прочитать ровно этот размер. Ошибка handle, чтения
  или несогласованный размер — отказ.
- macOS: получить путь через `_NSGetExecutablePath`, разрешить необходимый размер
  буфера, открыть результат только для чтения (`open`), зафиксировать размер через
  `fstat` и прочитать его. Ошибка пути/дескриптора/чтения — отказ.

Дескриптор закрывается после проверки. Эти операции не защищают от владельца
`root`/ядра, который может заменить файл или память; это явно остаточный риск модели.

## Форматный контракт Protector и SDK

Общие требования для трёх форматов: целые арифметические операции проверяют переполнение;
все смещения и размеры лежат в файле; диапазоны данных не пересекаются с метаданными;
неизвестные варианты отклоняются. Protector обязан менять только перечисленные ниже поля и
новые нулевые структуры. Структурные нарушения входа классифицируются как `MG-P05`, уже
существующий канонический раздел или псевдоним — как `MG-P06`, а невыполнимый layout
преобразования — как `MG-P07`, согласно полной очередности ошибок. SDK выполняет те же
проверки, но применяет свою очередность `MG-V03`…`MG-V07`; он не принимает вредоносный
вход и не переписывает небезопасный layout.

### ELF64 little-endian x86_64

**Принимаемый вход:** `e_ident[EI_MAG] = 0x7f,'E','L','F'`, `EI_CLASS = 2`,
`EI_DATA = 1`, `EI_VERSION = 1`, `e_machine = 62`, `e_type` равен `ET_EXEC (2)` или
`ET_DYN (3)`. `e_ehsize = 64`, `e_shentsize = 64`; section header table,
`e_shstrndx` и секция строк (`sh_type = SHT_STRTAB`) должны быть присутствовать,
находиться в файле и не использовать extended numbering (`e_shnum = 0` или `e_shstrndx = SHN_XINDEX` — отклоняется).
Имена всех секций должны ссылаться внутрь `shstrtab`. Существующий `.mindguard` или
любое имя с префиксом `.mindguard` отвергается.

**Построение:** сохранить все исходные байты и заголовки программ. Выбрать
`metadata_offset = round_up(input_length, 16)`; промежуток до него — нулевой и
покрываемый. После placeholder добавить копию существующей `shstrtab` с
`.mindguard\0`, затем выровнять на 8 и добавить новую section header table. В новой
таблице скопировать все записи, у записи `shstrtab` заменить `sh_offset/sh_size` на
новую копию, добавить запись:

```
sh_name = offset_of(".mindguard")
sh_type = SHT_PROGBITS (1), sh_flags = 0, sh_addr = 0
sh_offset = metadata_offset, sh_size = 512
sh_link = 0, sh_info = 0, sh_addralign = 1, sh_entsize = 0
```

Обновить в ELF header `e_shoff`, `e_shnum` (старое + 1) и оставить корректный
`e_shstrndx`. Число секций после добавления должно помещаться в `u16` и не требовать
extended numbering. Новая секция не входит в `PT_LOAD`, поэтому добавление не меняет
память загрузчика; все добавленные таблицы и изменённые поля покрываются digest.

**Проверка:** SDK разбирает активную (указанную `e_shoff`) таблицу, требует ровно одну
секцию с точными type/flags/offset/size, проверяет границы и отсутствие пересечения с
ELF header, program header table, section header table и другими секциями. Старые
байты прежней таблицы, если они остались в файле, являются обычным покрываемым overlay.
Файл без полноценной таблицы или с некорректными строками отклоняется.

### PE32+ little-endian x86_64

**Принимаемый вход:** DOS `MZ`, `e_lfanew` указывает на `PE\0\0`; COFF
`Machine = 0x8664`; optional header `Magic = 0x20b`, размер `0xf0`;
`NumberOfRvaAndSizes = 16`; все 16 data-directory записей находятся внутри
optional header; все заголовки и section raw-диапазоны находятся в файле, секции не
перекрываются. `FileAlignment`
обязан быть ровно `0x200`; `SectionAlignment >= FileAlignment` и является степенью
двойки; `SizeOfHeaders` выровнен и содержит существующую таблицу секций. Data directory `IMAGE_DIRECTORY_ENTRY_SECURITY` (индекс 4) должен иметь нулевые
поля `VirtualAddress/file-offset` и `size`: v1 не обрабатывает Authenticode. Поле optional-header `CheckSum` должно быть нулём. Наличие
существующего `.mguard` либо имени, начинающегося с `.mguard` и не равного точным
7-байтным ASCII + `NUL`, — отклоняется. Число секций после добавления не превышает `u16`.

**Приёмочное место до вставки (`pre-insertion` only):** новый 40-байтный section
header записывается сразу после старой таблицы. Для входного файла Protector обязан
проверить, что этот диапазон целиком лежит до `SizeOfHeaders`, до первого файлового
раздела (`file-backed`) с `SizeOfRawData > 0` и состоит из нулей; иначе Protector
возвращает `MG-P07` (`UNSAFE_LAYOUT`). Эти ровно 40 нулевых байт — исключительно
предусловие приёмки входа Protector перед записью нового header. Это условие входа не
переносится на уже преобразованный файл: после вставки те же байты содержат активный
section header и обычно ненулевые.

Так не требуется сдвигать существующие секции. Произвольный overlay до конца файла
разрешён и покрывается, но security directory с overlay запрещён.

**Построение:** выбрать
`metadata_offset = round_up(input_length, 0x200)`, где округление выполняется с
проверкой переполнения. Для PE32+ это смещение и его raw endpoint обязаны быть
представимы в нативных `u32` полях: в частности, требуется
`metadata_offset <= UINT32_MAX - 512`, а `metadata_offset + 512` вычисляется без
переполнения и помещается в допустимый диапазон `PointerToRawData`/`SizeOfRawData`.
Все вычисления endpoint для существующих и нового raw-диапазона, а также `RVA`,
`VirtualAddress + max(VirtualSize, SizeOfRawData)` и `SizeOfImage` после округления
обязаны не переполняться и быть представимы в соответствующих нативных полях PE.
Если требуемое новое смещение, размер, raw/RVA endpoint или итоговое поле нельзя
представить, Protector возвращает `MG-P07` и ничего не переписывает.

После проверки этих условий дописать нулевой padding и placeholder 512 байт. Новый
header имеет имя `.mguard\0`, `VirtualSize = 512`, `SizeOfRawData = 512`,
`PointerToRawData = metadata_offset` и `VirtualAddress = round_up(max(old
SizeOfImage, max(section.VirtualAddress + max(VirtualSize, SizeOfRawData))),
SectionAlignment)`. `Characteristics = 0x40000040` (`IMAGE_SCN_CNT_INITIALIZED_DATA |
IMAGE_SCN_MEM_READ`), остальные неиспользуемые поля нулевые. Увеличить
`NumberOfSections` на один и установить `SizeOfImage = round_up(VirtualAddress + 512,
SectionAlignment)`; выбор `VirtualAddress` через старый `SizeOfImage` не допускает
размещения внутри уже зарезервированного виртуального диапазона. Остальные directories
не менять.

**Проверка после вставки (`post-insertion`):** SDK требует ровно один активный
`.mguard` с указанными raw/virtual-размерами и проверяет, что сохранённые в нём
`PointerToRawData`, `SizeOfRawData`, их endpoint, все `RVA` и виртуальные endpoint
представимы в своих нативных ширинах и не переполняются. SDK проверяет активный новый
section header, точное размещение диапазона метаданных, отсутствие пересечения с
DOS/NT/section headers, другими raw-секциями или security directory, а также все
структурные bounds. Для PE SDK также обязан проверить, что `metadata_offset <=
UINT32_MAX - 512`, `metadata_offset + 512` и каждый сохранённый
`PointerToRawData + SizeOfRawData` представимы в `u32` без переполнения; нарушение
этих требований классифицируется как `MG-V03`. После активной структуры применяются
обычные проверки фиксированного блока, Ed25519 подписи (`MG-V12`) и SHA-256 дайджеста
(`MG-V13`); SDK **не требует**, чтобы исторический диапазон старого 40-байтного
header slack оставался нулевым: после вставки он является активной структурой и
проверяется как таковая. Нарушение representability, bounds или структуры даёт
`MG-V03`; несовпадение фиксированного содержимого/размещения — `MG-V07`. Входные
предусловия Protector (`pre-insertion`) и проверка финального output (`post-insertion`)
являются разными проверками. PE с non-zero Authenticode directory или
неподдержанным alignment отвергается, а не переписывается частично. Protector не
выпускает Authenticode подпись; любое изменение файла после защиты (включая
последующую подпись) естественно нарушит SHA-256.

### Mach-O 64 little-endian x86_64

**Принимаемый вход:** magic `0xfeedfacf` (`MH_MAGIC_64`), `cputype = 0x01000007`
(`CPU_TYPE_X86_64`), корректные `ncmds`/`sizeofcmds` и полностью расположенные в
файле команды загрузки (`load commands`). Fat/universal и big-endian варианты отклоняются. Существующий
`__MINDGUARD`/`__mindguard` или имена с соответствующим префиксом, а также любой
`LC_CODE_SIGNATURE` отклоняются: автоматическое Apple code signing не входит в v1.
Все сегменты и их файловые диапазоны должны быть проверяемы и не переполняться.

**Приёмочное место до вставки (`pre-insertion` only):** конец текущих команд загрузки
(`load commands`) — `cmd_end = 32 + sizeofcmds`. Должен существовать ведущий
file-backed сегмент с `fileoff = 0`, содержащий Mach-O header. Вычислить `payload_start`
как минимум `fileoff` каждого другого file-backed сегмента (`fileoff > 0`,
`filesize > 0`) и `offset` каждой существующей секции с `size > 0` и
`offset >= cmd_end`. Если таких диапазонов нет, `payload_start = input_length`. Все
вычисленные файловые диапазоны обязаны лежать в `[0, input_length)`; выход за EOF —
`MG-P05` (`MALFORMED_INPUT`). Секция, частично пересекающая `[cmd_end,
payload_start)`, — структурно неверна. Требуется `payload_start >= cmd_end + 152`, а
каждый байт `[cmd_end, payload_start)` должен быть нулём. Эти ровно 152 нулевых байта
— исключительно предусловие приёмки входа Protector перед записью нового
`LC_SEGMENT_64`; после вставки они содержат активную load command и не обязаны быть
нулевыми.

Новый `LC_SEGMENT_64` (72-байтный заголовок + 80-байтный `section_64`) записывается
ровно по offset `cmd_end` в эти 152 байта; сдвиг существующих данных не выполняется.
Если ведущего сегмента, достаточного pre-insertion slack или проверяемых ranges нет,
Protector возвращает `MG-P07` (`UNSAFE_LAYOUT`).

**Построение:** выбрать `metadata_offset = round_up(input_length, 0x1000)`,
проверяя переполнение и требование представимости в `u32`; дописать нулевой padding и
placeholder. Новый сегмент и секция имеют:

```
segment.cmd = LC_SEGMENT_64 (0x19), cmdsize = 152
segname = "__MINDGUARD" + NUL padding
fileoff = metadata_offset, filesize = 512
vmaddr = round_up(max(existing vmaddr + vmsize), 0x1000)
vmsize = 0x1000, maxprot = initprot = VM_PROT_READ (1)
nsects = 1, flags = 0
section.sectname = "__mindguard" + NUL padding
section.segname = "__MINDGUARD" + NUL padding
addr = vmaddr, size = 512, offset = metadata_offset (u32)
alignment exponent = 4 (16-byte), reloff/nreloc/flags/reserved* = 0
```

`metadata_offset` и `metadata_offset + 512` должны помещаться в `u32`, а арифметика
`vmaddr + vmsize` — в `u64`; все raw/virtual endpoint вычисления обязаны быть
непереполняющимися в нативных ширинах. Непредставимое значение даёт `MG-P07`.
Увеличить `ncmds` на один и `sizeofcmds` на 152; в Mach-O header поле `sizeofcmds`
заменяется на `old sizeofcmds + 152`, а прочие команды и offsets не меняются. Новый
read-only сегмент не содержит исполняемого кода. Его `vmsize` больше file size
намеренно (нулевая страница хвоста); этот виртуальный хвост не является файлом и не
входит в digest.

**Проверка после вставки (`post-insertion`):** SDK требует ровно одну активную секцию
с точными именами внутри ровно одного сегмента, проверяет активные `cmdsize`, поля
сегмента и секции, raw-диапазон `[metadata_offset, metadata_offset + 512)`,
представимость `offset`/endpoint в `u32`, арифметику виртуальных endpoint в `u64`, а
также отсутствие пересечения диапазона метаданных с Mach-O header, командами загрузки
(`load commands`) и файловыми диапазонами других сегментов/секций. SDK **не требует**,
чтобы исторический диапазон старого 152-байтного load-command slack оставался
нулевым: после вставки это активная команда, и проверяется её содержимое. Нарушение
структурных bounds/переполнений/представимости даёт `MG-V03`; несовпадение активной
фиксированной структуры или размещения — `MG-V07`. После активной load command
применяются обычные проверки фиксированного блока, Ed25519 подписи (`MG-V12`) и
SHA-256 дайджеста (`MG-V13`). Входные предусловия Protector
(`pre-insertion`) и проверка финального output (`post-insertion`) являются разными
проверками. Наличие code signature, fat binary или необходимость сдвига команд
загрузки/автоматической Apple подписи остаются отказом с fail-closed; Protector не
переписывает такой файл «на глаз».

## Ключи и конфигурация

### Внешний private-key файл Protector

Единственный формат `--key-file` в v1 — **ровно 32 сырых байта** Ed25519 seed,
без BOM, ASCII, hex, PEM, символа новой строки или дополнительных байтов. EOF должен следовать
сразу после байта 31; размер 0, 32+ или 64-байтный expanded key — ошибка `MG-P09` (`KEY_INVALID`).
Protector выводит стандартный (RFC 8032-совместимый) 32-байтный открытый ключ из seed.
Seed читается только из внешнего файла/секрета CI, не копируется в output/SDK/log/fixture
и после использования очищается настолько, насколько это гарантирует реализация.
Документация и репозиторий не содержат даже тестового закрытого ключа.

### Конфигурация открытого ключа SDK

Канонический переносимый вид — файл или значение конфигурации из ровно 64 ASCII
символов нижнего hex (`[0-9a-f]`), без пробелов, BOM и завершающего newline. Декодирование
даёт ровно 32 сырых байта открытого ключа Ed25519. Встраивание `uint8_t[32]`, `&[u8; 32]`
или эквивалента разрешено, если байты совпадают с этим декодированным значением.
SDK отвергает uppercase, whitespace, неправильную длину и любые списки из нескольких ключей.
Открытый ключ никогда не читается из метаданных для установления доверия; метаданные содержат
только проверяемый `trusted_key_id`.

## Таксономия ошибок

Коды стабильны для тестового стенда; в боевом режиме `verify_or_terminate()`
не возвращает их, а вызывает `abort`.

| Код | Область | Смысл |
|---|---|---|
| `MG-P01` | Protector | `INPUT_IO`: входной файл не прочитан |
| `MG-P02` | Protector | `OUTPUT_IO`: создание, запись временного файла или flush не удались |
| `MG-P03` | Protector | `UNSUPPORTED_FORMAT`: неизвестная сигнатура контейнера |
| `MG-P04` | Protector | `UNSUPPORTED_ARCH`: не поддержан x86_64 или little-endian вариант |
| `MG-P05` | Protector | `MALFORMED_INPUT`: нарушены границы или структура |
| `MG-P06` | Protector | `DUPLICATE_METADATA`: канонический блок или псевдоним уже присутствует |
| `MG-P07` | Protector | `UNSAFE_LAYOUT`: нельзя безопасно добавить структуры |
| `MG-P08` | Protector | `KEY_IO`: `key-file` нельзя открыть или прочитать |
| `MG-P09` | Protector | `KEY_INVALID`: key-file не соответствует формату |
| `MG-P10` | Protector | `CRYPTO_FAILURE`: SHA-256/Ed25519 или self-verification не выполнены |
| `MG-P11` | Protector | `OUTPUT_EXISTS`: `--output` уже существует или равен `--input` |
| `MG-P12` | Protector | `ATOMIC_RENAME`: не удалось опубликовать результат атомарно |
| `MG-P13` | Protector | `INTERNAL`: иная ошибка реализации; output не публиковать |
| `MG-V01` | SDK | `SELF_FILE_IO`: путь, handle, чтение или размер executable неверны |
| `MG-V02` | SDK | `UNSUPPORTED_FORMAT`: magic или вариант не поддержан |
| `MG-V03` | SDK | `MALFORMED_FORMAT`: границы, переполнение или таблицы нарушены |
| `MG-V04` | SDK | `METADATA_ABSENT`: каноническая секция не найдена |
| `MG-V05` | SDK | `METADATA_DUPLICATE`: найдена более одной канонической секции |
| `MG-V06` | SDK | `METADATA_UNKNOWN`: псевдоним или неизвестный кандидат блока |
| `MG-V07` | SDK | `METADATA_MALFORMED`: повреждены фиксированная раскладка, reserved или размер |
| `MG-V08` | SDK | `VERSION_UNSUPPORTED`: `protocol_version != 1` |
| `MG-V09` | SDK | `COVERAGE_UNSUPPORTED`: `coverage_rule != 1` |
| `MG-V10` | SDK | `KEY_CONFIG_INVALID`: конфигурация открытого ключа неверна |
| `MG-V11` | SDK | `KEY_ID_MISMATCH`: SHA-256 открытого ключа не равен полю |
| `MG-V12` | SDK | `SIGNATURE_INVALID`: Ed25519 не подтверждена |
| `MG-V13` | SDK | `DIGEST_MISMATCH`: SHA-256 покрытия не равен полю |
| `MG-V14` | SDK | `INTERNAL`: иная ошибка; всегда отказ по умолчанию |

Если причина подходит нескольким категориям, для SDK и Protector выбирается первая
применимая проверка в соответствующем нормативном списке раздела «Полная нормативная
очередность ошибок»; различие диагностического кода не влияет на abort.

## Семантика `verify_or_terminate()`

Высокоуровневая функция Rust и C++ имеет одинаковый контракт и вызывается в начале
запуска, до чувствительной работы. При полностью корректном файле она возвращает
`void`/управление (конкретная сигнатура API может быть идиоматичной для языка). При
любой ошибке, включая неизвестный формат/версию, отсутствие, дубликат или структурно неверные
метаданные, неверные идентификатор ключа, подпись или дайджест, она немедленно завершает процесс без
раскрутки стека. Нельзя заменить эту функцию проверкой только в отладочной сборке,
перехватить её ошибку и продолжить или считать лог доказательством успеха.

## Golden fixtures и межъязыковая совместимость

Репозиторий реализации должен хранить fixtures отдельно от этого контракта в
следующем логическом виде (в этом документе и в текущем репозитории закрытый ключ не
создаётся):

```
golden/v1/
  manifest.txt
  valid/
    elf64le.bin
    pe32plusle.bin
    macho64le.bin
  mutations/
    <fixture-id>/
      code-byte.bin
      data-byte.bin
      header-byte.bin
      table-byte.bin
      metadata-offset.bin
      metadata-size.bin
      signature-byte.bin
      digest-byte.bin
      metadata-truncate.bin
      metadata-duplicate.bin
      metadata-absent.bin
      unknown-version.bin
      unknown-coverage.bin
      reserved-nonzero.bin
      key-id.bin
```

### Обязательные отрицательные Ed25519-векторы

Набор `golden/v1/mutations/` обязан содержать отдельные негативные категории для
строгого профиля Ed25519 (без реального закрытого или иного секретного материала):

- `ed25519-noncanonical-public-key` — неканоническая compressed encoding настроенного
  открытого ключа; ожидаемый код `MG-V10`;
- `ed25519-noncanonical-R` — неканоническая compressed encoding `R`; ожидаемый код
  `MG-V12`;
- `ed25519-S-ge-L` — scalar `S >= L` (неканонический `S`); ожидаемый код `MG-V12`;
- `ed25519-small-order-public-key` — открытый ключ, кодирующий точку малого порядка;
  ожидаемый код `MG-V10`;
- `ed25519-small-order-R` — `R`, кодирующий точку малого порядка; ожидаемый код
  `MG-V12`.

Каждая категория должна иметь вектор для каждого поддерживаемого контейнера, сохранять
остальные байты неизменными настолько, насколько допускает мутация, и проверяться
обоими независимыми SDK с одинаковой первой категорией ошибки. Векторы не должны
содержать seed, private key или иные реальные ключевые секреты.

`manifest.txt` — UTF-8, LF, одна запись на строку `key=value`, без пробелов вокруг
`=`, с ключами в фиксированном порядке:

```
fixture_id=<ASCII без пробелов>
binary_format=ELF64LE|PE32PLUSLE|MACHO64LE
public_key_hex=<ровно 64 lowercase hex>
metadata_offset=<десятичное u64>
metadata_size=512
artifact_digest_hex=<ровно 64 lowercase hex>
signature_hex=<ровно 128 lowercase hex>
signed_prefix_hex=<ровно 192 lowercase hex>
expected=accept|reject
error=MG-Vxx|none
```

Путь в `valid` содержит готовый финальный бинарный файл; `public_key_hex` — только
открытый ключ. Для каждого `mutations/<fixture-id>` сохраняется тот же размер/формат,
если имя не говорит об усечении/дубликате. Указанные мутации должны включать
изменения кода, данных, заголовков и таблиц ELF/PE/Mach-O, каждого поля метаданных,
удаление, дублирование и усечение. Для каждой мутации оба SDK обязаны вернуть
одинаковый результат принятия/отказа и, во внутреннем диагностическом стенде, одну и ту же первую категорию
`MG-Vxx`. Ни один fixture не содержит закрытый ключ.

Rust Protector обязан генерировать корректные векторы, затем Rust SDK и независимый C++ SDK
проверяют их; обратный набор должен быть создан C++/внешним тестовым генератором без
использования общего Rust core. Система CI сравнивает байт-в-байт `artifact_digest`,
`signed_prefix`, `signature`, смещения/размер метаданных и итог проверки. Дополнительно
каждая реализация должна прочитать векторы, созданные другой, и прогнать все
негативные мутации. Любое расхождение — ошибка совместимости, а не допустимая
«особенность платформы».

## Ограничения выпуска

После успешной защиты нельзя менять ни один байт файла вне диапазон метаданных, включая
подпись PE/Mach-O, упаковщик, установщик, подпись кода, таблицы или padding: такое
изменение корректно обнаружится как `DIGEST_MISMATCH`. Нельзя также переносить или
растягивать секцию без повторной финализации. Protector обязан завершаться с
ошибкой до записи, если безопасный контракт формата не выполнен; частично
переписанный бинарник никогда не считается защищённым.
